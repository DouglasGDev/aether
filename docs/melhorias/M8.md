# M8 — integridade de download conferida por tamanho, não por hash

Task #92 do lote. Frente delegada com dono único de `src-tauri/src/ai/download.rs`
e `src-tauri/src/ai/catalog.rs`. Este doc é lido do diff desta árvore e de
medições rodadas nela; nada aqui é estimado nem "deveria dar".

## O defeito

`stream_to_file` publicava o `.part` com `std::fs::rename` depois de conferir
**só a contagem de bytes**: recusava excesso (`erros.maisBytesQuePublicado`) e
recusava falta (`erros.downloadIncompleto`). Um corpo com o tamanho exato e o
conteúdo trocado passava nos dois testes e ganhava o nome definitivo. Um GGUF é
um arquivo que o motor abre por offset: um byte trocado no meio de 2,2 GB não é
"o modelo com um probleminha", é outro arquivo — ou a carga recusando, ou a
carga aceitando e respondendo outra coisa.

O que a retentativa já cobria (rede caindo, servidor silencioso, 416, 404,
*Parar*) continuava coberto; o que não havia era nenhuma resposta para
**conteúdo errado com tamanho certo**, que é justamente o caso em que o `.part`
parece trabalho pronto.

## 1. De onde vem o hash publicado — lido da API real

Nenhum código do Aether fala com a API do HuggingFace: o `weights_bytes` do
catálogo foi **lido** arquivo por arquivo de `tree/main` (CONTRIBUTING.md:55-58).
Fui ler a mesma resposta, agora procurando o campo da soma.

Comando (resposta inteira: 5.086 bytes, 19 entradas, `http=200`):

```
curl -s https://huggingface.co/api/models/ibm-granite/granite-4.2-3b-GGUF/tree/main
```

O recorte de um arquivo GGUF do catálogo — o `granite-4.2-3b-Q2_K.gguf`, cujos
1.455.736.352 bytes já estavam no catálogo:

```json
{
  "lfs": {
    "oid": "a66f94672d05104517ae844664cac86086f627e29f8e6410bce4c42849afc71b",
    "pointerSize": 135,
    "size": 1455736352
  },
  "oid": "46c91364b0f80c1da3f2553f9d35e66e9d2d9789",
  "path": "granite-4.2-3b-Q2_K.gguf",
  "size": 1455736352,
  "type": "file",
  "xetHash": "3b125b05d55262ce4b4c8fec3cfa5da0225ef811b624fb8293a7170ced7c41a7"

```

**O campo do sha256 é `lfs.oid`.** Não é `oid` e não é `xetHash`, e isso foi
medido baixando os bytes e somando, não inferido do nome:

```
curl -sL https://huggingface.co/Qwen/Qwen3-Embedding-0.6B/resolve/main/tokenizer.json -o qwen-tok.json
curl -sL https://huggingface.co/ibm-granite/granite-4.2-3b/resolve/main/tokenizer.json -o granite-tok.json
python -c "
import hashlib
for n in ('qwen-tok.json','granite-tok.json'):
    b=open(n,'rb').read()
    h=hashlib.sha1(); h.update(b'blob %d\0'%len(b)); h.update(b)
    print(n, len(b), hashlib.sha256(b).hexdigest(), h.hexdigest())
"
```

Saída (rodadinha duas vezes, mesma coisa):

```
qwen-tok.json    11423705 def76fb086971c7867b829c23a26261e38d9d74e02139253b38aeb9df8b4b50a 6207337006f63c5a1b4efaa7ca0bfe479e35927b
granite-tok.json  7153414 883975314d58743726347caaf2c32ac89afd5ad57222cffbc4f052f2ab27b2d7 109016081083c2a3bba91a2111acb68656426fde
```

Contra a API (`tree/main` de `Qwen/Qwen3-Embedding-0.6B`, recorte):

```json
{"lfs":{"oid":"def76fb086971c7867b829c23a26261e38d9d74e02139253b38aeb9df8b4b50a",
        "pointerSize":133,"size":11423705},
 "oid":"18a4abbf4a40...","path":"tokenizer.json","size":11423705,"type":"file",
 "xetHash":"7f7828f2f177..."}
```

Lado a lado:

- arquivo **Git LFS**: `sha256(dos bytes servidos)` == `lfs.oid`, byte a byte. O
  `oid` do git (aqui `18a4abbf4a40…`) é a soma SHA-1 **do ponteiro**, não do
  conteúdo — conferir por ele seria conferir o arquivo errado. O `xetHash`
  (`7f7828f2f177…`) também é hex de 64 e também **não** é o sha256 do conteúdo
  servido; usei o campo que bate, não o que parece.
- arquivo **git comum**: o `oid` publicado **é** o SHA-1 de
  `blob <tamanho>\0<conteúdo>` — conferido: `109016081083c2a3bba91a2111acb68656426fde`
  bate com a segunda coluna. O sha256 do conteúdo (`883975314d58…`) não é
  publicado em lugar nenhum.

### Onde NÃO há hash publicado, e o que isso significa

Comando:

**batem 37 de 37**, hoje. A tabela nova não conserta tamanho divergente, só

## 3. A decisão sobre a divergência, e o caminho que ela abre

Um hash que não bate **não é marcado `Transitorio`**. `Transitorio` significa
"peça de novo do ponto onde parou, a rede é que caiu" — aplicado a um corpo
trocado isso pediriaRange os mesmos bytes errados, escreveria o mesmo `.part` e
estouraria as quatro tentativas dizendo "a conexão caiu 4 vezes seguidas", que
é mentira: a conexão não caiu, o corpo é outro. O `CorpoTroocado` é devolvido
para fora da fila de rede (`!eh_transitorio`), então:

1. o `.part` é apagado na hora da divergência (183);
2. o laço de **313** recomeça o corpo **do zero**, sem `Range`, no máximo
   `REINICIOS_POR_INTEGRIDADE = 2` vezes, com o mesmo backoff exponencial já
   usado entre pedidas e checando *Parar* durante a espera;
3. estourado o limite, a resposta é o `CorpoTroocado` com **medido e esperado
   lado a lado** e o número de recomeços, e nada é publicado — nem o `.part`
   sobrevive.

Por que recomeçar e não parar na primeira: um CDN ou espelho servindo uma
remessa errada uma vez é um evento que passa, e o preço de passar é pedir o
corpo de novo. Por que um limite pequeno e não `TENTATIVAS`: cada recomeço já
roda a fila inteira de 4 pedidas, então o pior caso são 3 remessas × 4 conexões
= 12 conexões antes da resposta honesta chegar; insistir gigabytes por vez
contra um servidor que insiste em errar é o usuário esperando sem nada novo
acontecendo. Por que apagar o `.part` e não deixar para a pessoa decidir: o
`tamanhoForaDoCatalogo` e o `status().partial_bytes` da biblioteca dariam a
ver um corpo que se sabe errado, e a próxima tentativa do usuário o publicaria
pelo atalho de 432.

O caminho que isso abre é o oposto do que a retentativa paga: um download que
falha por conteúdo **não tem** trabalho aproveitable em disco. A UI mostra o
par de hashes; com ele, o maintenedor distingue "o catálogo está com a soma
errada" (medido bate com o `lfs.oid` atual da API) de "o servidor trocou o
corpo" (não bate com nada).

   tabela; não li, então não escrevi.
3. **Um peso já publicado não é re-somado.** `download.rs:397` devolve `Ok(0)`
   quando o arquivo final já tem o tamanho esperado, sem tocar a rede e sem
   somar. É o caminho do "Baixar" num modelo já instalado. Conferir ali custa
   uma leitura de gigabytes por clique; o lugar certo é um comando de
   verificação explícito (como `runtime::verificar`), na biblioteca, e isso é
   tela + commando, fora desta frente.
4. **Os apoios não têm tamanho esperado.** `fetch` passa `expected = None` para
   apoio (`download.rs:649`), então o apoio só tinha conferência de conteúdo
   quando o `lfs.oid` existe — e mesmo assim o tamanho não é conferido contra o
   catálogo. O `size` dos quatro apoios está publicado e eu li (`7153414`,
   `17677`, `207`, `9013` para Granite 3B; `12807982`/`16710` para Ornith;
   `11423705`/`9706` para Qwen). Passá-los a `Some` é dados novos no catálogo
   pedindo a mesma disciplina dos pesos; ficou de fora para este diff ser só o
   hash.
5. **A tabela expira quando o repositório muda.** Os 37+2 hashes são a resposta
   de `tree/main` em 2026-11-20. Se um dono de repositório republicar um peso, o
   download passa a falhar com `CorpoTrocado` e a linha da tabela tem de ser
   lida de novo — que é o comportamento correto (é para isso que a soma existe),
   mas o diagnóstico está no medido/esperado, não num "erro de rede".
6. **`xetHash` não foi entendido, por isso não foi usado.** É 64 hex e para o
   `tokenizer.json` da Qwen (`7f7828f2f177…`) não é o sha256 do conteúdo
   servido. Se alguém precisar de soma para os arquivos git comuns, o caminho é
   perguntar à API (ou adicionar SHA-1 do blob, que exige dependência nova) —
   não é um trabalho de copy-paste.
